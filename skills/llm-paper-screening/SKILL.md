# LLM / Agent RL 论文筛选

把检索结果变成阅读和研究决策。用户以往明确要求先广泛搜索，再挑近一年最值得精读的工作，逐篇判断**核心创新、相比已有方法的实质区别、实验是否扎实、值得继续做什么**。本次给定的范围、时间和数量优先。

## 选择范围

- **广搜**：未指定主题时，以 LLM 后训练和多轮 Agent RL 为主。优先关注 RLVR、SFT/RL/OPD/OPSD 及配方控制、工具调用与交互环境、过程反馈与奖励验证、信用分配、rollout/训练效率。持续学习、RSI、可解释性与局部权重更新在与当前问题有关时纳入。一般 RL 工作需要有明确的迁移路径。广搜默认回溯近 12 个月，最多推荐 10 篇精读，证据足够的条目不足时少列。
- **已有候选**：先筛用户提供的候选，保留其中的旧论文并标日期。需要补强基线或追踪后续时另列外部工作，不混入候选名次。围绕种子论文追踪时同时检查前作、独立复验、反例和后续改进，并确认后续论文实质使用或检验了该方法。
- **落地调研**：先明确现有瓶颈和要验证的目标，再按落地价值排序。用户问“能否接入”“最可能落地”或“做哪一个实验”时读 [迁移与最小验证](references/transfer.md)。

## 广搜与证据核查

1. 按机制和问题拆分检索词，覆盖 NeurIPS、ICML、ICLR 等会议正式论文集和 OpenReview，以及国内外高校、研究机构、大厂的 arXiv 预印本、官方技术报告与研究发布。按主题补充相关会议。用多轮检索和引用链拓宽来源，避免集中于一个机构、一类方法或一种表述。名气、引用和热度用于找候选，入选由内容决定。
2. 给出实际检索起止日。近一年默认以首次公开日期为准。范围外的经典工作作为基线，窗口内正式发表或新增关键实验证据的旧预印本单独标注变化和时间；用户指定按发表或更新日期时采用其口径。合并同一工作的 arXiv、会议版和技术报告，引用证据所在版本，区分主会、workshop、预印本与官方报告。
3. 先从摘要和任务设定筛相关性，再读入围工作的正文、主要结果及必要附录。至少核对主要结论对应的表图、实验设置和最接近的方法。给出作者论文和适用的官方代码、数据或评测链接。摘要可作线索；关键结果只见摘要或二手引述时标为待核。报告实际覆盖的方向和明显缺口，未找到直接先例时限定在已查范围内。
4. 核查实现时区分“作者有仓库”“核心算法、配置和数据可获取”“可复现主要结果”。必要时定位训练入口、关键文件与版本。只给 README、缺权重或数据、未核实许可证或依赖时分别说明。无代码影响复现优先级，仍可推荐有独特研究价值且证据充分的工作。
5. 对每篇入围论文核查以下信息，链接直接来源，并标注实时统计的查询日期。将这些信息作为项目活跃度和作者背景，精读排序仍按研究内容和证据。
   - **全体作者署名单位**。以所引论文版本首页、作者脚注或会议官方作者信息中的署名为准，汇总去重后列出全体作者的所有单位，并单独标出第一作者及共同一作对应的单位。保留同一作者的多重署名，按论文所列名称区分不同院校、公司和研究机构。只把明确标为署名单位的组织纳入清单。来源未披露或对应关系无法确认时标明缺项。
   - **GitHub 最近更新与星标**。从论文、作者或机构项目页确认主官方仓库。最近更新时间统一用 GitHub 默认分支最新一次提交的日期，链接到提交或提交记录。星标用该仓库当前的精确总数，只有缩写时注明约数。无官方 GitHub 时标为“未找到官方仓库”，个别字段无法获取时标为“未核实”。多个核心仓库分别标注，星标分别报告。
   - **第一作者 Google Scholar 总引用数**。从论文确认第一作者，在其公开 Google Scholar 个人主页核对姓名、机构或代表论文，再取 `Citations` 的 `All` 列并链接主页。论文明确标注共同一作时分别列出。无公开主页、同名无法确认或页面无法访问时标为“未核实”并说明原因。

## 怎么取舍

| 判断 | 具体看什么 |
| --- | --- |
| 问题是否相关 | 对应哪一类任务、训练环节或失败模式。多轮任务关注模型是否根据新观察调整动作并完成目标。 |
| 创新是否实质 | 相对最接近的基线，具体改了数据、rollout、监督/奖励、loss 或权重更新的哪一步。能否说清谁生成轨迹、谁提供反馈、哪些 token 或参数收到更新。 |
| 证据是否扎实 | 是否有强而可比的基线、能隔离核心改动的消融，以及对应主张的留出或迁移验证。核对模型、数据、采样/教师/测试时预算与指标口径。按适用性检查多 seed、方差或任务粒度的统计。 |
| 哪项研究值得做 | 能否提出一个具体可证伪的后续问题，指出现有证据缺的是什么，以及哪个对照最能补齐。 |
| 能否复现或迁移 | 可获得的代码、环境、数据和基座，所需改动及全链路成本。只有适用条件明确时才推荐近期试验。 |

- **值得精读**：与问题直接相关，有实质机制变化、重要的新证据或能改变判断的反例。先按相关性与研究价值取舍，再以证据强弱排序，并写明明显的比较缺口。
- **选读 / 待核**：主题贴近但关键证据不足，或只能借用局部机制。把值得验证的部分及所缺材料写清楚。纯概念路线图可作背景，并注明其贡献类型。
- **暂缓**：只有关键词、名次或规模优势，关键增益无法与数据、基座或预算差异拆开，且缺少独立研究价值。明确区分“作者未报告”“本次未核实”和“已有反证”。避免伪精确总分。
- **值得试验**单列。优先能在当前系统检验、有公平对照且成本可控的候选。区分论文已验证的结论、基于设定作出的迁移推断、尚待验证的方案。多个模块组合时，写清各自承担哪段反馈或学习，以及组合本身的证据。

## 交付

默认中文。先给排序与理由，短表可用“优先级｜论文与日期｜核心变化｜最强证据和最大缺口｜阅读/复现建议”。精读条目再展开四个判断：**创新、最接近的对照、实验质量、后续研究机会**。引用结果时同时给指标、模型/任务、基线和表图或章节；百分比与百分点按原口径写。按用户需要给优先阅读的章节、核心代码位置或最小实验。精读数不足时给实际数量和原因；有用的经典基线、待核候选与落地排名分开展示。

每篇精读条目附“全体作者署名单位｜GitHub 默认分支最近提交日期｜GitHub 星标数｜第一作者及其署名单位与 Google Scholar 总引用数”。可汇总为一张表，查询日期相同时统一注明。
