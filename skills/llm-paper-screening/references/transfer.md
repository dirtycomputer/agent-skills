# 从论文筛选到最小验证

仅在用户需要接入、复现或排序实验方向时使用。沿用用户本次给出的基座、框架、数据、环境和预算。历史上的 7B–8B、单机 8 卡、3–7 天是一种曾用场景，当前预算未知时按假设给出可调方案。

## 把方法放回已有闭环

- 先说明当前失败、目标指标、可改环节和已有基线。对 verl 等明确到 rollout、环境交互、reward/verifier、数据管道、trainer/loss、评测或 checkpoint；有代码时核对实际版本和入口，再判断是否已有能力。
- **Agent RL / 工具环境**：检查轨迹是否执行有状态工具，反馈是环境状态、结果验证器还是 judge。区分格式正确、调用成功、状态达成和整任务成功。检查多步恢复、非法或重复写操作、替代合法路径，确认训练和评测使用的上下文、工具返回与线上假设相容。
- **SFT / RL / OPD / OPSD**：检查轨迹由谁生成，教师在学生哪段历史上使用什么额外信息，监督哪些位置。确认环境返回与模型生成的 mask、teacher 输入、损失归一化和数据/策略版本。蒸馏、奖励与配方搜索的增益分别归因。
- **Reward / verifier**：检查学习信号与独立任务结果能否相互验证，确认错操作等关键违规能否被其他得分抵消。复杂奖励头对比能回答同一问题的简单模型。评估 judge 误判、奖励利用以及外部反馈的费用。
- **RSI / 可解释性**：明确每轮究竟更新 prompt、skill、记忆、adapter 还是模型参数，记录反馈、候选、验收、拒绝或回退闭环。区分读出、干预定位和训练后任务收益；测试探针能否在 checkpoint 更新后继续使用。选择更新位置时对比随机、简单启发式和低成本梯度探针，固定可训参数量，计入诊断、重拟合及试训开销。

## 把第一轮缩成能回答问题的实验

1. 写出一个可证伪假设和一个主要改动。对比当前方案与能检验同一假设的简单基线，必要时加一个去掉关键机制的消融。尽量固定起点、数据、环境、训练与推理预算；无法配平的开销单列。
2. 说明训练数据、开发集、封存测试集、benchmark 及其版本/链接。优先按任务模板、环境或时间切分，避免同一任务变体、答案或筛选信号泄漏到留出集。只把实际可取得、确认适配的资源作为确定依赖。
3. 同时给目标任务成功率、能力保留或关键违规指标，以及 GPU 时、rollout/教师 token、外部调用、评估和存储成本中适用的项。明确接受、停止或回退标准。只在能获得这些信息时提供预算数字或区间，并写明估算依据。
4. 排序时区分“复现论文结果”和“把机制迁移到自己的任务”。可以先做低成本迁移验证。候选的开源程度影响可执行性，是否能在独立任务上验证决定结论强弱。

## 取舍示例

- 反馈条件蒸馏如果在可验证代码任务有效，可以列为精读。要接入客服 Agent，需要另测真实工具状态、局部反馈归因和不可逆错误。第一轮可用相同 rollout 对比已有 OPSD、全轨迹反馈和局部证据反馈；只有在同预算下局部反馈带来额外增益，才进一步拆解证据来源与 mask。
- 可解释性方法如果只证明提高了概念读出率，可以优先阅读机制。用于 RSI 自动选权重时，先在同等可训参数量与总计算预算下验证它能否优于随机位置和梯度探针，并报告目标收益、保留能力及选择成本。
